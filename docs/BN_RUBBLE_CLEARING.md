# BN rubble clearing

Examine furniture with the rubble examine action to clear it. DIG 3 or BURROW takes 60 game seconds; DIG 2 takes 120 seconds; weaker examine tools fail with the shovel message. Activating a digging tool offers clearing for nearby RUBBLE furniture, including rubble without an examine action. That separate BN tool path takes 30 / max(DIG-1,1) seconds. The occupied-site examine/tool UI asks before clearing when a vehicle, trap, monster, or NPC is present.

Completion places the real furniture bash item-group drops on the exact source tile and removes only the rubble furniture. Existing sealed contents, terrain, and the digging tool remain. Movement cancels; completion also rechecks distance, furniture identity, current BURROW/tool quality, and possession. No output is created on cancellation, replacement, lost tool, remote work, or an already cleared tile.

Source: BN iexamine.cpp:1321–1345, iuse.cpp:2812–2847, activity_handlers.cpp:3170–3183. The existing activity and item-group systems provide cancellation, deterministic drops, map/save tracking, and charge-stack merging.

## Follow-up: unfinished progress across save/load, and the NPC helper bonus

BN serializes the player's current activity and backlog directly (savegame_json.cpp:545,550,877,880: `data.read`/`json.member("activity"/"backlog", …)`), so a reload never loses `moves_left`, and `player_activity::can_resume_with` (player_activity.cpp:693) only resumes a cancelled/interrupted clear at the *same tile* (`coords[0]`) with the *same `index`* — iexamine.cpp's rubble() always assigns index −1, iuse.cpp's clear_rubble() assigns the DIG-quality `bonus` — so switching tool/path starts over. This engine's generic `Activity` is intentionally dropped on load (src/save/format.ts: "CDDA also drops the current activity on load"), so `src/game/rubble.ts` tracks its own `PendingRubbleClear` per tile (same tile + index keys as BN) in a new `rubble` save section (`installRubble`, wired from `installNature`): furniture id (to detect a since-replaced site), the activity index, the total duration frozen at first activation, and the game-seconds done so far. Re-examining/re-activating a matching, unexpired pending clear resumes with the remaining time and **does not pay tool energy again** — BN never re-invokes `iuse::clear_rubble` on a resume, so the energy already paid at the original activation is never repeated. A stale entry (furniture changed) is discarded and the next attempt starts fresh, cleanly; a missing/weak tool still fails with the existing "If only you had a shovel…" message, leaving any valid pending entry untouched for a later attempt with a better tool.

NPC helper speed bonus: `iuse::clear_rubble` reads `character_funcs::get_crafting_helpers(*p, 3)` (character_functions.cpp:807; iuse.cpp:2832) — awake NPCs obeying the player (`is_obeying`, not asleep), within pickup range with a clear path, capped at 3 — and applies `moves = moves * (10 - helpers.size()) / 10` *before* dividing by the DIG-quality bonus. This only applies to the tool-activation route; `iexamine::rubble` never queries helpers. `clearRubbleHelpers` in rubble.ts mirrors this (awake, `isFollower()`, same z, a clear `lineOfSight`), using this project's existing CRAFT_RANGE (2 tiles; crafting_inv.ts already shrinks BN's PICKUP_RANGE of 6 for 3D) rather than the literal BN tile count, to match the established adaptation. The count is read once when the activity (re)starts, exactly like BN's `moves_total`/`index` (fixed at `iuse::clear_rubble`'s single call, never recalculated for a resume): a helper joining or leaving mid-clear does not change a clear already under way. (BN also carries a separate, continuously-recalculated `activity_speed`/`complex_moves` assistant factor, up to 8 helpers, that this project does not model — matching the existing choice not to model that system's light/stat/tools factors for this activity either.)
